# 首次登录完善资料设计

## 目标

将名称和头像设置从注册流程中移出。注册仅创建邮箱密码账号和一次性恢复码；用户首次手动
登录后，必须在独立页面填写名称并选择头像，完成后才能进入 AI 学习打卡主页。

本设计覆盖 `2026-07-27-email-password-auth-design.md` 中“注册时选择头像、注册后自动登录”
的旧约定。邮箱密码、恢复码、打卡、图片和资料编辑能力保持不变。

## 用户流程

### 注册

1. 用户只填写邮箱、密码和确认密码。
2. 服务端创建已确认邮箱的 Supabase Auth 用户。
3. 数据库创建未完成引导的 profile，并写入恢复码摘要。
4. 注册接口返回 profile 和仅展示一次的恢复码，但不创建登录会话。
5. 用户确认已保存恢复码后返回登录页。

注册阶段使用内部默认头像 `avatar_key = 1` 和现有 `Attention_XXX` 默认名称。二者仅用于
保证 profile 在首次登录前结构完整，不作为已完成资料。

### 首次登录

1. 用户在登录页输入邮箱和密码。
2. 登录成功后进入应用入口。
3. 服务端读取 profile；若 `onboarding_completed = false`，重定向到 `/onboarding`。
4. 用户必须填写 1-20 个字符的名称，并从 5 个头像中选择一个。
5. 保存成功后，数据库原子更新名称、头像和完成状态，再进入打卡主页。

完善资料页不提供跳过按钮。提交失败时保留当前输入并显示通用错误，不提前进入主页。

### 后续登录与访问控制

- 已完成引导的用户登录后直接进入打卡主页。
- 未完成引导的用户访问主页时始终重定向到 `/onboarding`。
- 已完成引导的用户访问 `/onboarding` 时重定向到主页。
- 未登录用户访问主页或 `/onboarding` 时重定向到登录页。
- 用户完成引导后，现有资料弹窗继续允许修改名称和头像，但不改变邮箱。

## 数据模型

`public.profiles` 新增：

```text
onboarding_completed boolean not null default false
```

`complete_registration` 创建 profile 时显式写入 `false`。新增
`complete_profile_onboarding` RPC，在一个数据库操作中：

1. 校验目标 profile 属于指定用户；
2. 更新规范化后的名称和头像；
3. 将 `onboarding_completed` 设为 `true`；
4. 返回更新后的 profile。

RPC 放在现有服务端账户边界中，只允许 `service_role` 执行。普通资料更新 RPC 不修改
`onboarding_completed`，避免其他资料操作意外跳过首次登录流程。

生产项目当前聚合数据为零，因此迁移不需要兼容正式旧用户。本地已有测试账号在应用新迁移
后会进入一次完善资料流程。

## API 与领域契约

- `registerInputSchema` 改为 `{ email, password }`。
- 注册服务端固定使用默认头像，不接受浏览器提供的头像。
- 注册服务不再执行最终 `signIn`，成功响应不设置登录会话。
- `AccountProfile` 增加 `onboardingCompleted: boolean`。
- 新增 `onboardingInputSchema`：`{ displayName, avatarKey }`，两个字段均必填。
- 新增 `POST /api/onboarding`，仅允许已登录且尚未完成引导的用户调用。
- `GET /api/me` 和资料更新响应包含 `onboardingCompleted`。

重复提交 onboarding 时采用幂等成功或返回当前已完成 profile，不允许把完成状态恢复为
`false`。

## 页面与交互

### 注册页

- 移除头像选择区域。
- 保留邮箱、密码、确认密码和“返回登录”。
- 主按钮文案改为“创建账号”。
- 恢复码弹窗关闭动作改为退出到 `/login`，不再进入主页。

### 完善资料页

- 路由为 `/onboarding`，沿用现有认证卡片视觉体系。
- 标题为“完善你的学习身份”。
- 包含名称输入框和 5 个头像选项。
- 头像必须明确选择；默认头像不预选，避免用户无意识提交。
- 主按钮为“进入学习空间”。
- 页面不显示退出以外的跳过入口；可提供“退出登录”作为账号切换操作。

桌面端和移动端均保持单列紧凑表单，复用现有头像资源、选中态和无障碍单选语义。

## 错误与安全

- 注册接口忽略或拒绝额外的 `avatarKey`，防止旧客户端继续控制默认资料。
- onboarding 名称继续执行 NFKC、空白折叠、长度和控制字符校验。
- 头像仅允许整数 `1-5`。
- 服务端从当前会话确定用户 ID，不接受浏览器传入用户 ID。
- 未完成引导不影响密码登录、退出和恢复码找回。
- API 响应和日志不记录邮箱、密码、恢复码或 Supabase 密钥。
- 生产迁移必须在本功能实现、审查和本地测试完成后统一应用，避免连续修改生产 Schema。

## 测试

### 单元测试

- 注册表单不渲染头像选项，提交体不包含 `avatarKey`。
- 注册服务创建 profile 后不调用 `signIn`。
- onboarding 输入要求名称和头像同时存在。
- onboarding API 拒绝未登录请求、非法名称、非法头像和伪造用户 ID。
- 已完成与未完成 profile 的页面重定向正确。

### 数据库测试

- 新 profile 的 `onboarding_completed` 为 `false`。
- onboarding RPC 原子更新名称、头像和完成状态。
- RPC 只允许 `service_role` 执行。
- 普通资料更新不能重置或伪造 onboarding 状态。

### 集成与端到端测试

- 注册成功后没有登录会话，关闭恢复码后回到登录页。
- 首次登录强制进入 `/onboarding`。
- 未完成用户不能直接访问打卡主页。
- 完成名称和头像后进入主页，刷新和再次登录不再出现 onboarding。
- 完成后仍可在资料弹窗修改名称和头像。
- 云端部署后 profile 行与 onboarding 状态均写入目标 Supabase 项目。

## 发布顺序

1. 实现并验证本设计。
2. 重置本地 Supabase 并运行数据库、单元、集成和 E2E 测试。
3. 确认生产项目仍为空且写入保持关闭。
4. 一次性应用所有待处理邮箱认证和 onboarding 迁移。
5. 推送 Auth Hook 配置并验证 Email 开启、Phone 关闭、公共注册关闭。
6. 将预览或部署环境切换到云端变量。
7. 由用户完成首次邮箱注册、手动登录、完善资料和打卡验证。

## 完成标准

- 注册页不再要求名称或头像。
- 注册成功后必须手动登录。
- 首次登录必须填写名称并选择头像。
- 未完成用户无法进入打卡主页。
- 完成状态跨刷新、退出和设备保存在 Supabase。
- 生产迁移前本地全量门禁通过，生产迁移后云端 profile 可见。
