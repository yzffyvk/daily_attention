# Agent 上下文工程：API 结构、缓存与内容设计

资料：[上下文工程](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter2.md)

用户提炼要求：空；采用产品默认的系统提示词。

本地真实任务：`317834ad-ef9c-430b-b248-d0bb7e2b2c03`

一句话主旨：上下文工程通过显式管理 API 消息结构、保持静态前缀稳定、按需加载知识与状态并在必要时压缩历史，把 Agent 需要的信息高效地组织到每次模型调用中。

主要骨架：

核心问题：如何系统性地设计和管理 Agent 的上下文，使其在缓存、注意力与成本约束下最大化任务能力？

内容类型：运行机制与流程、方法与决策规则、概念与边界

阅读顺序：上下文 → 系统提示词 → 工具定义 → 用户消息 → 模型回复 → 工具执行结果 → 注意力机制 → KV Cache → Prompt Cache → 提示工程 → Agent Skills → 状态栏 → 上下文压缩

沿骨架展开：

### 上下文
包含系统提示词、工具定义、用户消息、模型回复和工具执行结果；静态部分组成前缀，动态轨迹随交互增长。上下文质量是能力关键。

### 系统提示词
定义身份、规则、约束和工作流程；与工具定义构成静态前缀，修改会导致 KV Cache 失效，应保持字节级稳定。

### 工具定义
独立于消息列表，质量直接影响工具使用准确性；与系统提示词一起保持稳定，动态调整会破坏缓存。

### 用户消息
在 API 中以 user 角色存在，是动态轨迹的起点；Agent 框架还可能借用 user 消息槽位注入状态栏等元信息。

### 模型回复
角色为 assistant；多轮交互中之前回复被原样放回，让模型看到自己做过什么决策。

### 工具执行结果
角色为 tool；是上下文压缩的主要对象，用摘要替换原始输出可能影响缓存。

### 注意力机制
每生成新 token 都生成 Query 与前文 Key 匹配并加权 Value；存在位置偏好，开头与结尾更受关注。

### KV Cache
复用前缀保持不变的 token 的 K、V；修改前缀使变动点及之后缓存失效。动态信息应追加到末尾，是架构约束。

### Prompt Cache
构建在 KV Cache 之上，由服务商匹配请求前缀并复用之前计算结果；与 KV Cache 作用层级不同。

### 提示工程
通过结构化、流程驱动、细化业务规则和少量示例提升效果；受 KV Cache 约束，系统提示词应保持稳定。

### Agent Skills
先提供元数据目录，按需加载完整 SKILL.md；避免系统提示词膨胀，对 KV Cache 友好。

### 状态栏
显式提炼任务进度、工具计数等状态，引导注意力到关键信息；追加末尾避免破坏缓存。

### 上下文压缩
在两次调用之间预处理消息列表，通常批量压缩工具输出；压缩会损失部分缓存，需权衡。

关键辨析：

KV Cache 是单次推理内缓存，Prompt Cache 是跨请求复用相同前缀；状态栏复用 user 消息槽位但内容由框架生成；Skills 按需加载，区别于常驻工具定义；压缩修改历史需权衡缓存损失。
